3.1 · Cuándo sí y cuándo no

Más agentes no es mejor por defecto

Sí conviene

  • Subtareas paralelizables
  • Contextos que no caben juntos
  • Herramientas o permisos que conviene aislar
  • Equipos distintos mantienen cada agente

No conviene

  • Tareas secuenciales y cortas
  • La coordinación cuesta más que el trabajo
  • No hay forma de evaluar el resultado

Costos: más tokens, más latencia y errores que se propagan entre agentes.

Sesión 3 · Sistemas multi-agente

15 minutos. Empezar con un agente y buenas herramientas; dividir solo cuando los datos lo pidan. Cada agente relee contexto, así que el costo en tokens se multiplica. En la fábrica, el argumento principal es de permisos: quien escribe las pruebas no debe poder cambiar el código para que pasen, y quien despliega no debe tocar la aplicación.

Jerárquica en código: un grafo dentro de otro

def equipo(nombre: str, miembros: list) -> CompiledStateGraph:

    g = StateGraph(Estado)

    ... # miembros en cadena + líder

    return g.compile()

 

equipo_calidad = equipo("calidad", [analista, tester])

equipo_desarrollo = equipo("desarrollo", [backend, frontend])

 

grafo = StateGraph(Estado)

grafo.add_node("director", director) # decide qué equipo sigue

grafo.add_node("calidad", equipo_calidad) # un grafo como nodo

grafo.add_node("desarrollo", equipo_desarrollo)

grafo.add_edge("calidad", "director") # sube solo el resumen

grafo.add_edge("desarrollo", "director")

Topología multi-agente · la idea

Traspasos: el control pasa de un agente a otro

Todo vuelve al centro

Con un supervisor, cada paso regresa al centro aunque el siguiente sea obvio.

Un agente con todos los roles

Un prompt enorme que intenta ser recepción, altas y directorio a la vez.

Traspasos

El agente activo atiende hasta que decide pasar el control a otro con una herramienta de traspaso; la conversación viaja con él.

Usuario: «Quiero dar de alta a Paola y después ver el organigrama»

Sesión 3 · Topologías · LangGraph, documentación de sistemas multi-agente

2 minutos, dentro de los cinco del patrón. En los traspasos, o handoffs, no hay un centro. Hay un agente activo que conversa; cuando decide que otro debe seguir, llama a una herramienta de traspaso, como transferir_a_altas con un motivo, y el control pasa con toda la conversación. Es la topología típica de atención a clientes: recepción, ventas, soporte. Ventaja: cada agente tiene un prompt corto y no hay vueltas innecesarias al centro. Riesgo: el orden lo deciden los modelos, así que el control puede rebotar entre dos agentes. Pregunta: ¿cómo evitarían un rebote infinito entre altas y directorio? Con un límite de traspasos.

Topología · en código

Traspasos en código: herramientas que pasan el control

@tool

def transferir_a_altas(motivo: str) -> str:

    """Pasa la conversación al agente de altas y bajas."""

    return motivo

 

def nodo(s: Estado) -> Command[Literal["altas", "directorio", ...]]:

    resp = modelo().bind_tools(herramientas).invoke(s["mensajes"])

    if resp.tool_calls: # quiere traspasar

        llamada = resp.tool_calls[0]

        destino = llamada["name"].removeprefix("transferir_a_")

        return Command(goto=destino, update={"mensajes": [nota]})

    return Command(goto=END, update={"mensajes": [resp]})

 

class Estado(TypedDict):

    mensajes: Annotated[list, add_messages] # una conversación

Lo que lo distingue

Herramientas transferir_a_*: llamarlas es decidir quién sigue. Una sola conversación viaja con el control.

Compáralo con

Supervisor: allí el control siempre regresa al centro.

class Turno(BaseModel):

    aporte: str

    siguiente: Literal["analista", "tester", "desarrollador",

                       "revisor", "FIN"]

 

def par(nombre: str):

    def nodo(s: Estado) -> Command[Destino]: # Destino = todos

        t = modelo().with_structured_output(Turno).invoke(...)

        fin = t.siguiente == "FIN" or s["turnos"] >= MAX_TURNOS

        return Command(goto=END if fin else t.siguiente, update=...)

    return nodo

 

for nombre in ROLES:

    grafo.add_node(nombre, par(nombre))

grafo.add_edge(START, "analista") # la única arista fija

    listos = [a for a, (lee, escribe) in AGENTES.items()

              if all(p.get(c) for c in lee) and not p.get(escribe)]

    return listos[0] if listos else END

Sesión 3 · Conectar agentes con herramientas · A2A hace lo mismo entre agentes de distintos sistemas

MCP, Model Context Protocol, es un estándar abierto para conectar agentes con herramientas y datos. Sin él, cada agente escribe sus propios esquemas y conectores: con M agentes y N sistemas son M por N integraciones. Con MCP, cada sistema publica un servidor una vez y cualquier cliente lo usa. El servidor publica herramientas, recursos y prompts; en clase usamos solo herramientas. El cliente hace dos cosas: list_tools para descubrir qué hay, con su descripción y esquema, y call_tool para ejecutarla. Lo importante para el curso: MCP no cambia el bucle del agente, cambia de dónde salen las herramientas. A2A, Agent2Agent, es el estándar hermano para que un agente le delegue una tarea a otro agente de otro sistema; aquí solo lo mencionamos. Puente a la sesión 4: la descripción de la herramienta entra al contexto del modelo, así que un servidor MCP de terceros es código y texto que no escribimos. Es la cadena de suministro de ASI04: revisar, fijar versiones y publicar lo mínimo, de solo lectura.
