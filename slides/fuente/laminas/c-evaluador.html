Evaluador-optimizador en código: un ciclo con juez

def evaluar(s: Estado) -> Estado:

    escribir(carpeta, "correo.py", s["codigo"])

    escribir(carpeta, "test_correo.py", PRUEBAS) # la especificación

    r = subprocess.run(["pytest", "-q", carpeta], timeout=60, ...)

    return {"aprobado": r.returncode == 0, "error": r.stdout}

 

def decidir(s: Estado) -> Literal["generar", "__end__"]:

    if s["aprobado"] or s["intentos"] >= MAX_INTENTOS:

        return END

    return "generar"

 

grafo.add_edge(START, "generar")

grafo.add_edge("generar", "evaluar")

grafo.add_conditional_edges("evaluar", decidir) # el ciclo

Lo que lo distingue

Un ciclo en el grafo con tope, y un juez independiente: pytest en un subproceso, nunca exec().

Compáralo con

Reflexión: allí el revisor vive dentro del mismo bucle del generador.

Ejecútalo

python -m ejemplos.s2_flujos.evaluador

En tu fábrica

construir → verificar → construir en flujo_s2.py, con el log del error.

Fragmento simplificado de ejemplos/s2_flujos/evaluador.py · las líneas resaltadas son el patrón

El generador recibe una instrucción vaga y las pruebas exigen detalles de las reglas de negocio: normalizar a minúsculas, quitar espacios, mensaje exacto. Por eso suele fallar el primer intento y pasar el segundo con el error de pytest como contexto. Subrayar la regla del curso: quien decide si el trabajo terminó es pytest, no el agente. Y la de seguridad: el código generado se ejecuta solo con pytest, en un subproceso con tiempo límite.
