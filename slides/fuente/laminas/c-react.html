def react(pregunta: str, max_pasos: int = 5) -> str:

    mensajes = [{"role": "user", "content": pregunta}]

    for n in range(max_pasos):

        resp = cliente.messages.create(model=MODEL, tools=ESQUEMAS,

                                       messages=mensajes)

        mensajes.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use": # ya puede responder

            return "".join(b.text for b in resp.content if b.type == "text")

        for b in resp.content:

            if b.type == "tool_use":

                observacion = HERRAMIENTAS[b.name](**b.input)

                resultados.append({"type": "tool_result",

                    "tool_use_id": b.id, "content": observacion})

        mensajes.append({"role": "user", "content": resultados})

    raise RuntimeError("Se alcanzó el límite de pasos")

Lo que lo distingue

Un for que sigue mientras el modelo pida herramientas. El modelo decide cuántas vueltas; el código pone el tope.

Compáralo con

Plan-and-Execute: allí el siguiente paso se decide antes, no en cada vuelta.

Ejecútalo

python -m ejemplos.s1_razonamiento.react

Ejecutar en vivo antes de mostrar el código. Pregunta: «¿cuántas vueltas dio y por qué?». Luego señalar las cuatro líneas resaltadas: el for con tope, la condición de salida (stop_reason distinto de tool_use), la ejecución de la herramienta y la observación que regresa como mensaje de usuario. Esa última es la que más se olvida: sin ella el modelo no ve lo que pasó.
